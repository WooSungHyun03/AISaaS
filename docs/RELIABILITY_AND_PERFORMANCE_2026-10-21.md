# 예약 제작 · 업로드 · 수집 · 속도 개선 (2026-10-21)

운영 데이터는 건드리지 않았고, 아래 모든 측정은 로컬 스택(시드 데이터, mock 제공자, 유료 API 호출 없음)에서 했습니다.
"확인함"은 이번 작업에서 직접 실행해서 본 것, "확인 못 함"은 운영 환경이 있어야 볼 수 있는 것입니다.

## 1. 예약 제작 (블로그 · 광고 숏폼)

찾은 원인(코드 추적):

| # | 원인 | 영향 | 수정 |
|---|---|---|---|
| 1 | 예약 실행이 **한 번만 실패해도** 자동화가 `ERROR`로 영구 정지(`findDueAutomations`는 ACTIVE만 선택) | 일시적인 AI·네트워크 오류 한 번이면 그 뒤 모든 요일 예약이 조용히 멈춤 | 연속 **3회** 실패해야 멈춤. 수동 "지금 만들기" 실패는 예약에 영향 없음. 성공하면 실패 카운트 초기화 (`automations.consecutive_failures`) |
| 2 | 블로그 "바로 만들기"는 `DRAFT`로 저장되고, 설정에서 요일을 골라 저장해도 **켜지지 않음**. 화면에는 "매주 월·수·금 09:00"이 적혀 있어 켜진 것처럼 보임 | 사용자가 요일을 골라도 아무것도 만들어지지 않음 | 블로그 화면에 **'자동으로 만들기' 스위치**와 다음 제작 시각, 설정 수정에 같은 체크박스. 멈춘 상태(DRAFT/ERROR)는 화면에 그대로 표시 |
| 3 | 같은 슬롯을 두 틱이 동시에 집을 수 있음(이용권·내용 중복 위험) | 중복 제작 | `next_run_at` compare-and-set으로 슬롯을 먼저 잡은 틱만 실행(`claimDueSlot`) |
| 4 | 스케줄러가 멈췄다 돌아오면 며칠 전 슬롯이 아무 요일에나 실행될 수 있음 | "지정하지 않은 요일에는 만들지 않음" 위반 | 12시간 안의 놓친 슬롯은 **한 번만** 따라잡고, 그보다 오래된 슬롯은 건너뛰며 이력에 사유를 남김. 건너뛴 뒤에도 그 순간의 정규 슬롯은 잃지 않음 |
| 5 | 틱이 돌았는지 알 방법이 없음 | "cron이 불렸다"와 "콘텐츠가 만들어졌다"를 구분 못 함 | `scheduler_ticks` 하트비트, `/api/health/scheduler`(공개, 시각·정상 여부만), 관리자 `/admin/scheduler`(연속 실패·시간이 지났는데 안 돈 예약) |
| 6 | DB 스케줄러가 죽으면 대안이 없음 | 전부 정지 | Vercel Cron(하루 1회, `vercel.json`)이 같은 라우트를 GET으로 호출(Bearer `CRON_SECRET`). 슬롯 선점 덕에 둘이 겹쳐도 중복 없음 |

확인함: 월~일 각 요일의 다음 실행이 선택한 KST 요일 09:00인지(전 주 14일 × 7요일), 00:30·23:30 KST처럼 UTC 날짜가 다른 시각, 8주 시뮬레이션(월·수·금만 24회), 점검(몇 시간/며칠) 시나리오, 동시 3틱, 전체 로컬 e2e(`npm run e2e:schedule`): 슬롯 도래 → 블로그 글 생성 → `content_history` 저장 → 이용권 정확히 1회 차감 → 다음 주 같은 요일로 이동, 숏폼(개발 서버 mock)도 같은 흐름, 꺼짐/요일 변경이 즉시 반영.

숏폼 주의: **운영 빌드는 영상 생성기가 설정되지 않으면 실행을 거절**합니다(placeholder가 영상으로 보이면 안 되므로). 이 경우 예약은 "영상 제작 서비스가 아직 연결되지 않아…"라는 실패 이력을 남기고 이용권은 차감되지 않습니다. 실제 숏폼이 만들어지려면 Vercel에 `AD_VIDEO_PROVIDER=fal`, `FAL_KEY`, `AI_PROVIDER=anthropic`, `POSTPROCESS_PROVIDER=worker`, `POSTPROCESS_WORKER_URL/TOKEN` 이 모두 있어야 합니다(`docs/AD_SHORTS.md`).

## 2. 광고 영상 재료 이미지 업로드

원인: `ensureShortsBuckets`가 **매 업로드 준비 때** 버킷을 만들거나 갱신하면서 `fileSizeLimit`을 100MB/200MB로 요청합니다. 호스팅 Supabase는 프로젝트의 전역 업로드 한도(무료 50MB)를 넘는 버킷 한도를 거절하는데, 로컬 스택은 이 검사를 하지 않아 로컬에서만 잘 됐습니다. 거절되면 예외가 그대로 올라와 **사진을 포함한 모든 업로드**가 "업로드를 준비하지 못했어요"로 끝났고, 원인은 로그에도 남지 않았습니다. (같은 함수가 숏폼 제작 단계에서도 호출됩니다.)

수정: 서명 URL을 먼저 요청(버킷은 거의 항상 이미 있음) → 실패할 때만 버킷 준비 → 크기 한도가 거절되면 한도 없이 다시 생성(프로젝트 한도를 따름) → 이미 있는 버킷의 설정 갱신 실패는 업로드를 막지 않음. 실패는 `STORAGE_BUCKET` / `STORAGE_SIGN` 코드로 구분해 로그(원인·HTTP 상태)에 남기고, 화면에는 짧은 코드만 보여줍니다.

확인함: 단위 테스트 8개(한도 거절·이미 존재·서명 실패·재시도), 로컬 e2e 18/18(여러 장 업로드, 미리보기, 개별 삭제, 이전 사진 재사용, 사용자 간 접근 차단, 업로드한 사진이 숏폼 생성 입력에 들어감). 확인 못 함: 운영 Supabase에서의 실제 응답(운영 DB/스토리지 읽기 권한 없음). 영상(최대 100MB)은 프로젝트 전역 한도(무료 50MB)를 넘으면 업로드 단계에서 실패합니다 — Supabase 콘솔 Storage → Settings의 업로드 한도를 올리거나 50MB 이하 영상을 쓰세요.

## 3~4. 채널 수집 · "수집을 멈췄어요"

원인 두 가지:

1. **네이버 블로그 RSS(`rss.blog.naver.com`)의 robots.txt가 모든 크롤러를 `Disallow: /`로 막습니다.** 지난 작업에서 넣은 robots.txt 준수 때문에 네이버 RSS는 읽을 수 없고, 읽지 못한 날이 실패로 쌓여 중단 메시지로 이어졌습니다. robots.txt는 계속 지키며 우회하지 않습니다. 네이버는 공식 검색 API(키가 있을 때)로만 보강하고, 읽지 못하면 "측정 불가"로 표시합니다(0으로 채우지 않음).
2. 일시적인 오류(타임아웃·429·5xx)와 "채널이 없음"을 구분하지 않고 같은 연속 실패로 세어 12회에 영구 정지했습니다.

새 정책(`collect-pipeline.planFailure`):

| 상황 | 동작 |
|---|---|
| 일시적(타임아웃, 429, 5xx, 연결 실패) | 같은 날 30분 간격 재시도(서버가 `Retry-After`를 주면 그만큼), 3회 실패하면 다음 06:00 KST. 연속 실패가 길어지면 매일 → 이틀 → 주 1회로 간격만 늘림. **중단하지 않음** |
| 채널 없음(404 확정) | 하루 1번만 확인, **3일 연속**이면 일시중지(사용자 수정 필요 안내) |
| 우리 설정 문제(잘못된 API 키) | 채널 탓으로 세지 않고 6시간 뒤 다시 |
| 쿼터 소진 | 그 틱의 YouTube 호출을 멈추고 1시간 뒤 재시도(블로그는 계속) |
| robots 거부 / 비공개 / 공개 글 없음 | `UNAVAILABLE` + 사유 코드(`ROBOTS_DISALLOWED`, `FEED_NOT_FOUND`, `FEED_FORBIDDEN`…). 오류 아님, 매일 확인 |
| 중지된 채널 | 일주일에 한 번 자동으로 다시 확인, 응답하면 스스로 재개. "다시 진단하기"는 즉시 재검증 후 재개 |

과거 정상 데이터는 어떤 경우에도 지우지 않습니다. `tracked_channels.last_success_at`(마지막 성공 시각)을 따로 기록하고 카드의 "마지막 갱신"은 이 값을 씁니다.

확인함: 단위 테스트(`planFailure` 전 분기, 404/403/429/5xx 분류, Retry-After 파싱, 티스토리·네이버 수집기), 로컬 e2e(`npm run e2e:collection`). 확인 못 함: 실제 YouTube/네이버/티스토리 응답과 운영의 06:00 틱(운영 키·스케줄러 필요).

## 5. 성장 리포트 버튼 속도

원인: 기간·집계 버튼이 링크라서 **누를 때마다 서버 페이지 전체를 다시 렌더링**했습니다 — 사업체·채널·스냅샷(채널 수만큼 페이지 단위 순차 읽기)·영상별 통계·AI 해석(해당 기간의 오늘 해석이 없으면 **AI 호출을 끝까지 기다림**)·내부 기록 3종까지 10여 번의 DB 왕복이 줄줄이 이어졌습니다.

수정: 서버가 7/30/90일 값을 **한 번에** 계산해 내려보내고(`getGrowthBundle`: 지표별 90일 일별 점수 + 기간별 수치 + 기간별 영상 표 + 기간별 해석 + 내부 기록), 기간·일/주/월 전환은 브라우저에서 이미 받은 데이터를 자르고 묶기만 합니다(`lib/growth/select.ts`). 버튼은 누르는 즉시 선택 상태로 바뀌고(`useDeferredValue`), 요청이 없으며, 연속 클릭은 마지막 선택이 남습니다. AI 해석은 기다리지 않습니다: 오늘 만든 AI 해석이 있으면 그것을, 없으면 같은 숫자로 만든 규칙 요약을 먼저 보여주고 선택한 기간의 AI 해석은 백그라운드로 불러옵니다(채널·기간·하루 1회). 서버 쪽 읽기는 채널별로 병렬화했고 독립 조회는 한꺼번에 시작합니다.

검증: 브라우저가 계산한 일/주/월 × 7/30/90일 18개 조합이 서버가 요청마다 계산하던 값과 **완전히 같음**(`growth-bundle.test.ts`, 26개), e2e에서 버튼을 눌러도 서버 요청 0건.

## 6. 전체 사이트 속도

근본 원인: **함수 실행 지역**. 운영 응답 헤더가 `x-vercel-id: icn1::iad1::…`로, 엣지는 서울인데 서버 함수는 미국 동부(iad1)에서 실행되고 Supabase는 서울(ap-northeast-2)입니다. 페이지 하나가 보통 8~28번 DB/Auth를 부르고 그중 상당수가 순차라서 왕복(약 180ms)이 그대로 쌓입니다. 로컬 DB는 지연이 없어서 가려졌습니다.

수정(코드):
- `vercel.json`: `regions: ["icn1"]` — 함수를 DB와 같은 서울로. (확인 못 함: 배포 후 헤더로 확인)
- 매 요청 인증 확인을 로컬 JWT 검증(`getClaims`, 운영 프로젝트는 ES256 JWKS 사용)으로 — proxy와 레이아웃/페이지의 Auth 서버 왕복 제거. 같은 요청 안의 중복 `getUser()`는 `cache()`로 한 번만(26개 페이지).
- 앱 레이아웃: 프로필·이용권·관리자 여부를 순차 4번 → 병렬 1번, 체험 이용권 부여 RPC는 이용권이 0일 때만.
- 대시보드/블로그/숏폼/진단: 독립 조회를 동시에 시작. 진단 페이지는 AI 해석을 기다리지 않고 Suspense로 뒤따라 표시.
- 마이그레이션 `0076`: 수집 대기 인덱스 확장, `(channel_id, recorded_at)` 인덱스.

측정(`npm run perf:measure`, 프로덕션 빌드, 로컬 DB 앞에 **180ms 지연 프록시**를 둬서 운영과 같은 왕복 지연을 재현, 같은 세션 두 번째 로드):

| 화면 | 개선 전 TTFB / DOMContentLoaded | 개선 후 TTFB / DOMContentLoaded |
|---|---|---|
| 대시보드 | 1299 / 1491 ms | 421 / 825 ms |
| 마케팅 진단 | 1309 / 1477 ms | 400 / 797 ms |
| 캘린더 | 1290 / 1403 ms | 415 / 796 ms |
| 블로그 | 1280 / 1874 ms | 408 / 810 ms |
| 숏폼 | 1289 / 2066 ms | 401 / 990 ms |
| 성장 리포트 | 1269 / 2273 ms | 412 / 852 ms |
| 설정 | 1226 / 1305 ms | 415 / 494 ms |
| 요금제 | 1251 / 1291 ms | 404 / 605 ms |
| 이용방법 | 1269 / 1353 ms | 408 / 487 ms |

| 성장 리포트 버튼 | 개선 전 | 개선 후 |
|---|---|---|
| 최근 7·30·90일, 일별·주별·월별 | 선택 표시까지 2.27~2.34초, 요청 2건 | 선택 표시 45~96ms, 서버 요청 0건 |

(지연이 없는 로컬에서도 개선 전 200~330ms → 개선 후 약 50ms.) 이 수치에는 `icn1` 지역 변경 효과가 **포함되지 않았습니다**(로컬에서 재현 불가) — 같은 지역이 되면 남은 왕복이 수 ms로 줄어듭니다.

## 7. 로깅 · 장애 대응

- 예약: 틱 하트비트·결과 집계(`scheduler_ticks`), 슬롯을 놓쳤을 때/뺏겼을 때/멈췄을 때 구조화 로그(`automation_due_slot_missed`, `automation_due_slot_taken`, `automation_parked_after_failures`).
- 수집: 실패 로그에 `kind`·`code`·연속 실패 수·다음 시도 시각, 수집 기록(`channel_collection_runs`), 마지막 성공 시각.
- 업로드: 단계·HTTP 상태·원인 로그(`shorts_asset_upload_ticket_failed`), 사용자에게는 코드만.
- 사용자에게 내부 키·상세 오류를 보여주지 않고, 로그는 기존 `logger`의 민감 키 마스킹을 그대로 씁니다.

## 8. 배포 순서 (중요)

1. `npx supabase db push --linked` 로 **0076 먼저** — 새 코드가 `automations.consecutive_failures`, `tracked_channels.last_success_at`을 읽고 씁니다. 마이그레이션 없이 코드만 올라가면 예약 실행의 성공 기록이 실패합니다.
2. 코드 push(Vercel 자동 배포, 함수 지역 `icn1`, 일일 cron 등록).
3. 확인: `/api/health/scheduler`가 200이고 `ageMinutes`가 5 이하(DB 스케줄러가 살아 있다는 뜻), 응답 헤더 `x-vercel-id`가 `icn1::icn1`, 관리자 `/admin/scheduler`.
